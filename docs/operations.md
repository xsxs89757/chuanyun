# Operations cheat sheet

[English](operations.md) · [中文](运维.md)

The commands you'll actually type after the server is up. For first-time setup see
[Deploying the server](deploy.md).

Placeholders used below:

| Placeholder | Example |
|---|---|
| `<server>` | `1.2.3.4` or `tunnel.example.com` |
| `<suffix>` | `t.example.com` |
| `<control-port>` | `7000` (change it if frp already has it, e.g. `7100`) |

## Credentials

```bash
chuanyun-server user add zhangsan
```

The credential is **shown once** — only a hash is stored. Send it along with the
certificate fingerprint:

```bash
chuanyun-server fingerprint
```

The fingerprint isn't a secret; the same channel is fine.

**Lost credential** (or undoing a revoke):

```bash
chuanyun-server user reissue zhangsan
```

The old one stops working immediately and the live connection is dropped; they log in
again with the new one. `user add` refuses an existing name rather than overwriting it, so
a mistyped name can't knock someone offline.

**Someone leaves:**

```bash
chuanyun-server user revoke zhangsan    # revoke; live connection drops at once
chuanyun-server kick zhangsan           # disconnect only, credential stays valid
```

## Checking on it

```bash
chuanyun-server status                  # who's online, how many tunnels
chuanyun-server user list               # who has credentials, and expiry
systemctl status chuanyun-server        # is it running
journalctl -u chuanyun-server -f        # follow the logs
journalctl -u chuanyun-server -n 50 --no-pager
```

The admin interface is loopback-only, so these run on the server. They return JSON, which
is handy for monitoring:

```bash
curl -s localhost:<admin-port>/status
curl -s localhost:<admin-port>/tunnels
curl -s localhost:<admin-port>/users
curl -s localhost:<admin-port>/audit
```

> These endpoints reject requests carrying browser markers (`Origin` / `Sec-Fetch-Site`)
> and require a loopback `Host` — the threat being a malicious web page quietly probing
> your server's local ports. Don't expect them to open in a browser; use curl.

## Upgrading

Re-running the install command is the upgrade. Config and data are untouched:

```bash
curl -fsSL https://github.com/xsxs89757/chuanyun/releases/latest/download/install-server.sh | sudo sh
```

Tunnels blip for a couple of seconds while the service restarts, then clients reconnect on
their own. Addresses don't change.

**If GitHub is slow or blocked from the server**, install offline — fetch the files where
connectivity is good and copy them over:

```bash
# somewhere with working GitHub access
VER=0.1.4
B=https://github.com/xsxs89757/chuanyun/releases/download/v$VER
for f in chuanyun-server-$VER-linux-x86_64.tar.gz SHA256SUMS install-server.sh; do
    curl -fLO $B/$f
done
scp chuanyun-server-$VER-linux-x86_64.tar.gz SHA256SUMS install-server.sh root@<server>:/tmp/

# on the server
cd /tmp && CHUANYUN_BASE_URL=file:///tmp sh install-server.sh --version v$VER
```

`CHUANYUN_BASE_URL` can point at anything holding those files — a local directory, an
internal HTTP server, object storage. Checksums are still verified.

**Rolling back** is the same command with `--version`:

```bash
sudo sh install-server.sh --version v0.1.3
```

## Configuration

`/etc/chuanyun/server.toml`. Restart after editing:

```bash
sudo systemctl restart chuanyun-server
```

Misspelled keys are rejected rather than ignored — startup fails and `journalctl` names the
offending key.

The settings you'll actually touch:

```toml
[control]
listen = "0.0.0.0:<control-port>"        # bind address
public_addr = "<server>:<control-port>"  # what clients type; the download page shows it

[http]
domain_suffix = "<suffix>"

[admin]
download_dir = "/var/lib/chuanyun/downloads"
download_url = "https://<suffix>/download"   # where the client's update banner points

[limits]
max_tunnels_per_user = 10
```

**Upgrades never touch an existing config**, so settings added in a new version have to be
filled in by hand.

## The download page

Drop installers into the download directory and buttons appear:

```bash
sudo cp chuanyun-*.dmg chuanyun-*.msi /var/lib/chuanyun/downloads/
sudo chown -R chuanyun:chuanyun /var/lib/chuanyun/downloads
```

Only `.dmg`, `.msi`, and `.exe` are recognised; anything else there is neither listed nor
downloadable. **The packages here also drive the client's update prompt** — the next client
to connect sees "update available". Remove the old ones when you ship a new version:

```bash
sudo rm -f /var/lib/chuanyun/downloads/*0.1.3*
```

## nginx

Chuanyun's nginx config is **hand-written**, not generated by a control panel — it won't
appear in the panel's site list.

```bash
# with the baota panel, it lives here
ls /www/server/panel/vhost/nginx/<suffix>.conf

nginx -t && nginx -s reload    # always -t before reload
```

Back it up before editing. `nginx -t` catches syntax errors, but **never reload without
running it first** — a broken config takes every site on the machine down with it.

## Certificates

Wildcard certificates require DNS-01. Once acme.sh is set up it renews on its own (checks
four times a day, renews ahead of expiry) and the hook reloads nginx.

```bash
/root/.acme.sh/acme.sh --list                          # what's issued, when it renews
/root/.acme.sh/acme.sh --cron --home /root/.acme.sh    # run a renewal check now
```

If a certificate is near expiry and hasn't renewed (DNS credentials rotated, say), check the
log, then force it:

```bash
/root/.acme.sh/acme.sh --renew -d '*.<suffix>' --ecc --force
```

To see what a certificate covers and when it expires:

```bash
openssl x509 -in /path/to/fullchain.pem -noout -ext subjectAltName -dates
```

> **A wildcard certificate covers exactly one level.** A cert for `*.example.com` is **not**
> valid for `a.b.example.com`. If tunnels live under their own subdomain level, they need
> their own `*.<suffix>` certificate.

## Troubleshooting

**A client can't connect**

In this order:

```bash
nc -vz <server> <control-port>    # from the client machine
systemctl status chuanyun-server
chuanyun-server fingerprint       # does it match what the client has
```

Nine times out of ten it's **the cloud security group** not allowing the control port —
`ufw allow` only covers the OS firewall; the provider's layer is separate.

**The tunnel address shows a branded 404**

The request reached the server but matched no tunnel. Either the tunnel is switched off in
the client, or nginx isn't passing the Host header through
(`proxy_set_header Host $http_host`) — subdomain routing depends entirely on it.

**The service won't start**

```bash
journalctl -u chuanyun-server -n 30 --no-pager
```

Usually a port is taken (`Address already in use`). Find out who has it:

```bash
ss -tlnp | grep -E ':(7000|7080|7001) '
```

**Don't trust `systemctl is-active` alone.** A `Type=simple` service reports active the
moment it forks; combined with `Restart=always`, a service that crashes on startup cycles
through active / failed / activating, and `is-active` can catch one of those brief actives.
Use this instead:

```bash
chuanyun-server status    # answering means it really came up
```

**Who did what, when**

```bash
curl -s localhost:<admin-port>/audit | python3 -m json.tool
```

## Uninstalling

```bash
curl -fsSL https://github.com/xsxs89757/chuanyun/releases/latest/download/install-server.sh \
  | sudo sh -s -- --uninstall
```

Stops the service and removes the binary. **Config and data are deliberately kept** — the
data directory holds the self-signed certificate, and deleting it means handing every client
a new fingerprint. Remove it by hand once you're sure:

```bash
sudo rm -rf /etc/chuanyun /var/lib/chuanyun && sudo userdel chuanyun
```

nginx config and certificates are separate; clean those up yourself.
