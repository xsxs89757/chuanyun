# 发版

三样东西各有各的节奏，互不打扰。

## 客户端与服务端

打 tag 就行，CI 会在三个平台上构建并自动创建 GitHub Release：

```bash
git tag v0.1.0
git push origin v0.1.0
```

产出：

| 产物 | 说明 |
|---|---|
| `chuanyun-server-0.1.0-linux-x86_64.tar.gz` | 服务端静态二进制 + systemd 单元 + nginx 样例 |
| `chuanyun-0.1.0-macos-universal.dmg` | macOS 客户端（Intel + Apple Silicon 通用包） |
| `chuanyun-0.1.0-windows-x86_64.msi` | Windows 客户端 |
| `SHA256SUMS` | 上面三个的校验和 |

发版前把 `Cargo.toml` 里的 `version` 改好。**tag 必须和它对上**——CI 第一个 job
就是核对这个，对不上直接失败。原因是产物名里带版本号，而
[安装脚本](../scripts/install-server.sh)靠版本号拼文件名；不一致的话脚本会去下一个
404 的地址。

产物名一律用 ASCII：CI 的 `upload-artifact` 会把非 ASCII 字符吞掉（v0.1.0 第一次发
出来的 dmg 就变成了 `-0.1.0.dmg`）。.app 和 dmg 卷标仍然叫「穿云」，那才是用户看得见的名字。

### 服务端安装脚本

[`scripts/install-server.sh`](../scripts/install-server.sh) 是从 `main` 分支的 raw 地址直接
取的，不随 release 走——改了推上 main 就生效。它按 `--version`（默认查 GitHub 的 latest）
拼产物名，所以**改产物命名规则时必须同步改它**。

改完至少在容器里跑一遍：

```bash
docker run -d --name t --platform linux/amd64 --privileged \
  -v $PWD/scripts:/scripts:ro cy-systemd:amd64
docker exec -e CHUANYUN_BASE_URL=file:///rel t \
  sh /scripts/install-server.sh --domain t.example.com --version v0.1.0
```

`CHUANYUN_BASE_URL` 本来是给内网镜像用的，测试时正好拿来指向本地目录。

### 客户端怎么知道有新版

客户端在设置页点「检查更新」时，会去查 **GitHub Releases**——CI 已经把安装包
传到那里了，不需要再单独维护一份版本清单。

内部部署如果不想让客户端连外网，把品牌配置里的 `update_url` 指向自己的服务端：

```toml
# brand/company.toml
update_url = "https://tunnel.example.com/chuanyun/api/client/version"
```

服务端的管理接口已经提供了这个返回，形状客户端认识。

只提示、不自动安装——安装包没有代码签名，静默替换一个未签名的二进制不是好主意。

## Vite 插件

插件的版本和主程序无关，所以用自己的 tag 前缀：

```bash
# 1. 改版本号
cd integrations/vite-plugin-chuanyun
npm version patch          # 或 minor / major

# 2. 打 tag 推上去
git add -A && git commit -m "插件 v0.1.1"
git tag plugin-v0.1.1
git push origin main --tags
```

CI 会跑测试、核对 tag 与 `package.json` 的版本是否一致，然后 `npm publish`。

npm 包页面显示的是 `README.md`，所以插件目录里那份是**英文**的，中文在
`README.zh-CN.md`（`package.json` 的 `files` 里两份都带上了）。

### 一次性准备：Trusted Publishing

**不需要在仓库里存任何 npm 令牌。** 走 npm 的 Trusted Publishing（OIDC）：
GitHub Actions 每次发布时换一张一次性凭据，没有长期令牌可偷，也不会被两步验证拦住。

（npm 在 2026 年收紧了「绕过 2FA 的令牌」，2027 年 1 月起直接取消这类令牌的
发布权限，全面转向 OIDC。所以这条路不只是更省事，也是往后唯一的路。）

不过有个先有鸡还是先有蛋的问题：**npm 要求包已经存在，才能给它配置 Trusted
Publishing**（`npm trust` 命令也一样要求）。所以第一个版本得手动发一次。

#### 第一次：在自己电脑上手动发

**前提：npm 账号必须开着 2FA。** 现在所有新包的默认策略就是这样——没有 2FA
且没有绕过 2FA 的令牌，publish 一定 403。到账号设置里点 Enable 2FA 即可
（可能是扫码绑验证器，也可能直接用通行密钥，看你的浏览器）。

```bash
cd integrations/vite-plugin-chuanyun
npm login
npm publish --access public
```

**要在系统自带的终端里跑**，不能在 IDE 的内嵌终端里：npm 需要一个真正的
TTY 才能弹出验证提示或打开浏览器确认，否则会直接 403 而且不告诉你为什么。

这是唯一一次手动操作。（`0.1.0` 就是这么发出去的。）

#### 之后：配好 Trusted Publishing，从此全自动

1. 打开 <https://www.npmjs.com/package/vite-plugin-chuanyun/access>
   （或者包页面 → Settings）
2. 找到 **Trusted Publisher** 一节，点 **GitHub Actions**
3. 填：
   - Organization or user：`xsxs89757`
   - Repository：`chuanyun`
   - Workflow filename：`npm-publish.yml`
   - Allowed actions：勾上 **npm publish**
4. 保存

配完之后，以后每次打 `plugin-v*` 的 tag 就会自动发布，仓库里不用存任何密钥，
也不用再碰验证码。

可以顺手把之前加的 `NPM_TOKEN` 从仓库 secrets 里删掉了——它已经没用了，
留着反而是个风险。

#### 令牌那条老路（不推荐）

如果你确实想用令牌（比如从别的 CI 发布），要注意 npm 现在只有
**Granular Access Token**，而且能绕过 2FA 的那类正在被收紧。真要用的话，
在 <https://www.npmjs.com/settings/~/tokens> 生成时 Packages and scopes 选
**All packages** + **Read and write**，然后在 workflow 里加回
`NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`。

### 不想发 npm 也能用

包名 `vite-plugin-chuanyun` 目前没被占用，但如果你暂时不想发，
使用方有两条路（[插件说明](../integrations/vite-plugin-chuanyun/README.md)里也写了）：

**pnpm 直接从仓库子目录装**：

```bash
pnpm add -D "github:xsxs89757/chuanyun#path:/integrations/vite-plugin-chuanyun"
```

npm 和 yarn 不支持子目录，所以走 tarball：

```bash
cd chuanyun/integrations/vite-plugin-chuanyun
npm install && npm pack
# 把生成的 .tgz 发给同事，或者放公司内网
npm i -D /path/to/vite-plugin-chuanyun-0.1.0.tgz
```

`package.json` 里配了 `prepare` 脚本，所以从 git 装的时候会自己构建
（`dist/` 没有进仓库）。
